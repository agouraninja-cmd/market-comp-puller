# Dark Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A site-wide dark theme across the app and every public server-rendered page, following the OS preference on first visit with a header toggle to override.

**Architecture:** One pure module, `theme.js`, holds the semantic token table and emits `:root` / `[data-theme="dark"]` custom-property blocks. Server-rendered CSS consumes the tokens directly. `index.html` cannot, because its colors live in Tailwind class names rather than declarations, so it gets a bridge layer re-pointing each utility at a token. The whole bridge sits inside `@media screen`, which makes the existing `@media print` block unreachable by the theme.

**Tech Stack:** Plain Node (no dependencies), `node --test`, vendored Tailwind 3.4.17, Leaflet 1.9.4, html2canvas 1.4.1.

**Spec:** `docs/superpowers/specs/2026-08-10-dark-mode-design.md`

## Global Constraints

- **Zero npm dependencies.** This repo has none and must keep none.
- **No Tailwind regen.** The bridge is raw CSS inside `index.html`'s existing inline `<style>` element, not new utility classes. `tailwind.css` must not change. Do not run the regen command; if the Claude Code hook regenerates it after an `index.html` edit, verify `git diff tailwind.css` is empty before committing.
- **The light theme must not change**, with ONE measured exception, owner-approved 2026-08-10 (see below). Every token's light value is copied verbatim from the existing code, so a correct sweep is a visual no-op. Any rendered light-mode difference beyond the approved consolidation is a bug in this work, not an improvement.
- **The approved consolidation.** A token system means fewer tokens than hexes, so 15 near-duplicate values fold into a shared token and render a slightly different light colour. Measured maximum drift is ΔRGB 25 of a possible 441 (~6%), on hairlines and faint text only, and no folded colour is ever displayed beside its original. The full list, largest first: `#7A5B12`→`--warn-text` (25), `#8A93A0`→`--ink-faint` (25), `#B8C0CC`→`--ink-4` (20), `#D5DAE2`→`--line` (19), `#8F99A8`→`--ink-faint` (15), `#E2E8F0`→`--ok-bg` (14), `#94A3B8`→`--ink-faint` (13), `#EAEEF4` (10), `#ECEAE3` (9), `#46536A` (8), `#E3F2EA` (6), `#F7EFDC` (6), `#F8FAFC` (4), `#E7E3DA` (3), `#FCFBF8` (1). Reviewers: this is a decision, not a defect. Drift OUTSIDE this list still is a defect.
- **No em dashes are required either way in code comments** — match the surrounding file's style, which uses them freely.
- **`node --check server.js && npm test` must pass before every commit.** This is the `prestart` production deploy gate; a red suite means Render refuses to boot.
- **Editing `server.js` or `vault-page.js` requires restarting the process.** Editing `index.html` does not — it is read from disk per request.
- **`devlog.json` must be written as clean UTF-8.** Never with a PowerShell redirect lacking `-Encoding utf8`. CI fails the build on the mojibake pattern.
- **Shared checkout.** A second Claude session and a human collaborator share this working tree. Never `git add -A`. Stage explicit paths, and run `git status --short` immediately before staging.
- Out of scope: `/admin`, `/dev`, `/hq`, `/contacts`, and `email-shell.js`.

  // --red lightens for contrast as TEXT on a dark page; --red-fill stays
  // saturated because white text sits on top of it.
  assert.notEqual(THEME_TOKENS["red"].dark, THEME_TOKENS["red-fill"].dark);
  assert.equal(THEME_TOKENS["red-fill"].light, THEME_TOKENS["red"].light);
});

test("surfaces already dark in light mode lift rather than stay put", () => {
  // --slab is #1A2433 on light paper. If its dark value equalled --paper it
  // would dissolve into the page and the emphasis would vanish.
  assert.notEqual(THEME_TOKENS["slab"].dark, THEME_TOKENS["paper"].dark);
});

test("rootCss emits both blocks with every token", () => {

  assert.match(css, /^:root\{/);
  assert.match(css, /\[data-theme="dark"\]\{/);

    assert.ok(css.includes(`--${name}:${v.dark}`), `dark --${name} missing`);
  }

test("rootCss is safe to interpolate into a template literal", () => {

  // ${ in this string would end it and break the module that embeds it.
  const css = rootCss();

```js
// The site's colour tokens, light and dark. Pure: no I/O, no clock, no
// requires -- which is what lets `npm test` exercise the whole table with
// nothing running.
//
// The NAMES and every light value below are copied verbatim from the :root
// block vault-page.js and the four admin dashboards already share. That is
// deliberate and load-bearing: adopting the existing vocabulary means those
// pages inherit dark mode by swapping one block, and it makes it impossible
// for this work to shift a colour in the theme that already ships.
//
// Tokens added for site-wide coverage use ROLE names (--ink-body,
// --ink-mute, --ink-faint) rather than extending the --ink-N ramp, because
// --ink-2 is already #4C5665 and renumbering it would restyle five pages.
//
// Dark values come from the slate ramp index.html's own token comment
// already documents (slate-950 #020617 bookends, slate-900 #0F172A ink,
// slate-800 #1E293B lifted, slate-700 #334155 hover). No new brand colours.
const THEME_TOKENS = {
  // --- surfaces ---------------------------------------------------------
  paper:            { light: "#FBFBF9", dark: "#020617" }, // page
  card:             { light: "#ffffff", dark: "#0F172A" }, // card, above paper
  wash:             { light: "#F5F4EF", dark: "#1E293B" }, // lifted panel
  // Same light value as --wash on purpose: in light mode a hover above a
  // washed surface DARKENS, in dark mode it must LIGHTEN. One token cannot
  // express both directions, so this one changes nothing today.
  "wash-2":         { light: "#F5F4EF", dark: "#334155" },
  // Surfaces that are ALREADY dark in light mode (bg-[#1A2433], bg-slate-900,
  // the footer). Left equal to --paper they would dissolve into the page and
  // the emphasis they carry would vanish. They lift instead.
  slab:             { light: "#1A2433", dark: "#1E293B" },

  // --- rules ------------------------------------------------------------
  edge:             { light: "#D8D4C9", dark: "#334155" }, // primary border
  line:             { light: "#E4E2DA", dark: "#273244" },
  hair:             { light: "#F0EFE9", dark: "#1E293B" }, // hairline/divider

  // --- ink --------------------------------------------------------------
  ink:              { light: "#1A2433", dark: "#E2E8F0" },
  "ink-body":       { light: "#374253", dark: "#CBD5E1" },
  "ink-2":          { light: "#4C5665", dark: "#C2CCDA" },
  "ink-mute":       { light: "#5A6473", dark: "#AEBACB" },
  "ink-3":          { light: "#68707E", dark: "#94A3B8" }, // the workhorse
  "ink-faint":      { light: "#9AA2AD", dark: "#7C8899" },
  "ink-4":          { light: "#C7CBD2", dark: "#475569" }, // outlines, disabled

  // --- brand ------------------------------------------------------------
  // The split that a naive inversion gets wrong. #B91C1C fails contrast as
  // TEXT on a dark page, so links lighten to brand-400. A FILLED button must
  // NOT lighten, because white text sits on it -- it stays saturated.
  red:              { light: "#B91C1C", dark: "#F87171" },
  "red-deep":       { light: "#991B1B", dark: "#FCA5A5" },
  "red-fill":       { light: "#B91C1C", dark: "#DC2626" },
  "red-fill-hover": { light: "#991B1B", dark: "#B91C1C" },

  // --- status -----------------------------------------------------------
  green:            { light: "#15803D", dark: "#34D399" },
  "ok-text":        { light: "#06603A", dark: "#6EE7B7" },
  "ok-bg":          { light: "#E7F5EE", dark: "#0C2B21" },
  "ok-rule":        { light: "#BFE5D2", dark: "#155E43" },
  "warn-text":      { light: "#8A6D1A", dark: "#FCD34D" },
  "warn-bg":        { light: "#FBF3DC", dark: "#2A2410" },
  "warn-rule":      { light: "#EDDFB0", dark: "#5B4A16" },
  "err-bg":         { light: "#FCF1EF", dark: "#2A1517" },
};

// Emits both custom-property blocks as one line. Every in-scope stylesheet
// is a JS template literal, so this must never contain a backtick or a
// ${ sequence -- a test pins that.
function rootCss() {
  const decl = (key) =>
    Object.entries(THEME_TOKENS).map(([n, v]) => `--${n}:${v[key]}`).join(";");
  return `:root{${decl("light")}}[data-theme="dark"]{${decl("dark")}}`;
}

module.exports = { THEME_TOKENS, rootCss };
```

In `server.js`, directly below the `THEME_CSS` declaration added in Task 2:

```js
// Sets data-theme before the first frame. Render-blocking and inline on
// purpose: anything deferred or async paints the light theme first, and a
// white flash on a dark page is worse than having no dark mode at all.
// Wrapped in try/catch because localStorage throws outright in a Safari
// private window, and a theme preference must never be able to blank a page.
//
// It reads PRESENCE of an explicit choice, falling back to the OS. This is
// also the feature's rollback lever: nothing else in the codebase ever sets
// data-theme, so short-circuiting this one string disables dark mode on
// every surface at once.
const THEME_BOOT =
  `<script>(function(){try{var t=localStorage.getItem("theme");` +
  `if(!t)t=matchMedia("(prefers-color-scheme: dark)").matches?"dark":"light";` +
  `if(t==="dark")document.documentElement.setAttribute("data-theme","dark");` +
  `}catch(e){}})();</script>\n`;

// Paired so the mobile browser chrome agrees with the page it frames.
const THEME_META =
  `<meta name="theme-color" content="#FBFBF9" media="(prefers-color-scheme: light)"/>\n` +
  `<meta name="theme-color" content="#020617" media="(prefers-color-scheme: dark)"/>\n`;
```

## Notes for the implementer

**The one thing most likely to go wrong** is Task 2's sweep mapping a hex to the wrong token — for example turning `background:#B91C1C` into `var(--red)` instead of `var(--red-fill)`. That looks perfect in light mode, because both tokens hold `#B91C1C` there, and only shows up as a pale pink button in dark mode on one page. Step 5 of Task 2 and the `--red`-background test exist for exactly this. Read the CSS **property**, not just the value.

**The second** is assuming light mode is fine because the tests pass. Every task that touches a stylesheet has an explicit "verify light mode is unchanged" step. Do not skip them: the entire light theme is untested by anything automated, and this work rewrites its colour declarations wholesale.

**Rollback**, if any of this needs to come out after deploy: short-circuit the boot script (three places — `index.html`'s head, `THEME_BOOT` in `server.js`, and the vault's insertion, which shares `THEME_BOOT`). Nothing else in the codebase sets `data-theme`, so that disables every dark rule at once without touching the light theme.
